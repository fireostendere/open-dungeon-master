# Инструкция для AI-агентов (Open Dungeon Master / ODM)

Этот документ — главная точка входа для любой AI-модели (Antigravity, Claude Code, Cursor, OpenCode, Aider), открытой в этом проекте. Здесь описаны архитектура, боевой сервер, протокол внешнего мастера (DM) и правила ведения игры.

---

## 1. Параметры боевого сервера и инфраструктура

- **SSH подключение**: `root@api.iroslyakov.com` (доступ по ключу)
- **Корневая папка на сервере**: `/opt/odm`
- **Репозиторий на сервере**: `/opt/odm/repository`
- **Веб-приложение**: `https://dnd.iroslyakov.com` (Next.js 16, Node 22+, SQLite; прежний адрес `api.iroslyakov.com` оставлен как alias)
- **Администратор веб-панели**: логин `odm_admin`, пароль в `/opt/odm/config/admin.json`
- **MCP Control Plane**:
  - Внешний HTTPS endpoint: `https://dnd.iroslyakov.com/mcp`
  - Loopback endpoint на сервере: `http://127.0.0.1:3006/mcp`
  - Внутренний Control API: `http://127.0.0.1:3005/api/internal/mcp`
  - Токен авторизации (Bearer): `/opt/odm/config/mcp.token`
- **База данных**: SQLite в `/opt/odm/state/data/local-roleplay.sqlite` (ключ `DB_ENCRYPTION_KEY` в `/opt/odm/config/app.env`)

### Основные команды управления на сервере:
- `odmctl status` — проверка состояния приложения, активного коммита и базы.
- `odmctl update [--ref <git-ref>]` — сборка и деплой новой версии из репозитория.
- `odm-mcpctl status` / `odm-mcpctl sync` — проверка и сборка MCP-сайдкара.
- `odmctl logs` — просмотр логов основного контейнера.

## 2. Роль AI-агента: Внешний Мастер Подземелий (External Narrator)

Сервер ODM развёрнут в режиме `--runtime none` (без встроенной тяжёлой нейросети).
Внешняя модель берёт на себя роль **Ведущего (Dungeon Master)** через MCP-протокол (`odm_narrator`).

### Разделение обязанностей:
1. **Ты (AI-Мастер):**
   - Литературный нарратив, описание локаций, погоды, запахов и опасностей.
   - Отыгрыш неигровых персонажей (NPC) и чудовищ, диалоги.
   - Определение намерений игроков (Do / OOC / Direct); речь персонажа входит в Do.
   - Принятие решений о проверках и назначение сложностей (DC).
   - **ЖЕСТКОЕ ПРАВИЛО:** Никогда не придумывай результаты бросков костей текстом («ты выбросил 17»)! Все проверки, попадания и урон рассчитывает сервер.
2. **Сервер ODM (SRD Rules Engine & Dice):**
   - Ведёт листы персонажей (D&D 5e), характеристики, инвентарь, HP, КД, ячейки.
   - Физически бросает d20 со всеми бонусами и модификаторами через `request_roll`.
   - Управляет тактической картой, инициативой, неожиданностью, смертью врагов и выдачей лута.

### Строгий цикл разрешения действий (Action ➔ Engine ➔ Narration):
Для значимых неопределённых действий используется следующая цепочка; на
тривиальный гарантированный, невозможный или пассивно решённый правилами исход
бросок не назначается:
1. **Фаза 1: Заявка действия игрока (`kind: "do"`)**:
   - Игрок объявляет попытку персонажа (взлом замка, поиск потайных дверей/улик/лута, скрытное перемещение, лазание по стене, спасбросок от яда/магии, проверка проницательности/убеждения и т.д.).
2. **Фаза 2: Механическая проверка сервером (`narrator.invoke` -> `request_roll`)**:
   - Если исход действия неочевиден или несёт риск/последствия, Мастер вызывает
     доступное актуальное действие catalog: `request_roll` для проверки, но
     `pc_attack`/заклинание для боевой атаки. Поля `group_check` и других действий
     всегда бери из актуального `narrator.catalog`, не из примеров ниже.
   - **Сервер физически бросает d20**: генератор случайных чисел + характеристики из листа персонажа + владение навыком + бонусы/баффы (Bless, Bardic Inspiration) + преимущество/помеха (2d20kh1/kl1) + сравнение с DC.
   - Сервер сохраняет бросок и публикует событие `roll_result`. В интерфейсе стола появляется **отдельная карточка броска (`RollCard`)** с полной математикой, раскладкой кубов и цветовой подсветкой (золотое сияние при Натуральной 20, тлеющий багровый при Натуральной 1).
   - Ответ может оставить pending roll; последствия описываются только после
     подтверждённого `roll_result`, а не после исчезновения pending.
3. **Фаза 3: Повествование мастера отдельным сообщением (`narrator.narrate`)**:
   - ТОЛЬКО ПОСЛЕ завершения броска и отдельным следующим сообщением Мастер описывает последствия заявки, опираясь на результат броска.

### Жёсткие запреты для Мастера (Anti-Patterns):
- ❌ **Запрещено выдумывать успех или провал в тексте**: нельзя писать «ты открываешь шкатулку и находишь 120 золотых» без предварительного броска `request_roll` на взлом/силу.
- ❌ **Запрещено комкать несколько действий игроков в один нарратив без бросков**: если трое игроков написали «обыскиваю трупы», «взламываю шкатулку» и «готовлю засаду» — мастер обязан последовательно запросить броски для каждого действия перед описанием общего итога.
- ❌ **Запрещено писать игрокам в чат «бросай кубик на кнопку»**: все броски в системе инициирует AI-Мастер через `request_roll`. (Если у игрока включены физические кости, сервер сам заморозит игру и покажет окно ввода).
- ❌ **Сервер не имеет собственной языковой модели**: сервер пассивен и не читает художественный текст игроков. Если ты (AI-Мастер) не вызвал `request_roll`, бросок НЕ произойдёт, и игроки не увидят кубиков.

### Инициатива, строгость и восстановление
- При переходе к новому бою сначала прочитай актуальный `encounter` и входы.
  **До `start_encounter` и любых бросков инициативы** опубликуй короткую,
  энергичную открывающую сцену: где происходит столкновение, что его вызвало,
  кто из сторон виден и какая угроза возникает прямо сейчас. Не описывай исход
  атаки/броска и не раскрывай скрытых противников. Подтверди commit narration
  через read/readAfter; только затем один раз вызови `start_encounter` с UUID
  `commandId`, последними `expectedSeq` и `timelineEpoch`, перечитай порядок,
  ожидающую инициативу и current actor, и только после этого запроси инициативу.
  Если встреча уже активна, не запускай её повторно. Нет свободной атаки до
  инициативы и нет повторного старта при активном или неоднозначном ответе.
- Выбранные edition/source и явные house rules действуют на любой сложности.
  Автоматического fun/freeform/cinematic-success нет; только отдельная
  аутентифицированная команда оператора может назвать house rule, не игровой claim.
  Кости, ресурсы, приватность и safety сохраняются. Не ловить перебросы; исключение
  — правило даёт reroll либо реально изменились обстоятельства.
- `end_turn` завершает лишь объявленный законченный ход; narration не завершает
  ход. `release_floor` возвращает `hold.next`, не `open`, не пропускает инициативу
  или pending roll. Технический отказ допустимого D&D-запроса: один retry после
  read без новых бросков; приватный Ask/whisper не публикуется. Это не runtime:
  остановившийся host передаётся внешнему supervisor.

### Разделение ролей: Кресло Мастера (DM Seat) vs Места Игроков (Player Seats)
- В интерфейсе стола действует строгое разграничение:
  - **Пользователь в кресле Мастера (`human_dm_user_id`)**: не имеет листа персонажа, поле ввода переключается только на «Повествование» (Narrate) и «OOC».
  - **Игроки (`members` со статусом `player`)**: имеют лист персонажа и кнопки **«Действие» (Do)**, **«OOC»** (+ «Указание» у лидера). Реплики персонажа отправляются внутри Do.
- **Если создатель стола / оператор хочет играть как обычный игрок со своим героем:**
  - Он **НЕ ДОЛЖЕН** сидеть в кресле Мастера (`human_dm_user_id`).
  - В кресло Мастера сажается выделенный технический бот (например, `ai_dm`, id: `a7f4ccd7-8835-416b-b95e-149b99c8959f`).
  - После добавления бота в участники оператор MCP может назначить его через `odm_campaigns.assign_dm_seat` (`seat: "dm"`, `userId`: ID бота). Кандидат с игровым листом отклоняется.
  - Тогда создатель стола (например, `odm_admin`) играет за своего персонажа через «Действие» (включая реплики) и «OOC», а внешний AI ведёт игру через MCP от имени бота `ai_dm`.
  - Требования к кампании под MCP: `dmMode: "human"`, `ttsEnabled: false`, `mapsEnabled: false`, `status: "active"`, и `human_dm_user_id` указывает на бота `ai_dm`.

### Стандарт единиц измерения: метры и килограммы по умолчанию
- **По умолчанию любая кампания создаётся и ведётся в метрической системе (метры и килограммы)**:
  - Все дистанции, размеры помещений, радиусы заклинаний и скорость перемещения: 5 футов = 1.5 метра (1 клетка тактической карты), 10 футов = 3 метра, 30 футов = 9 метров (стандартная скорость персонажа).
  - Вес инвентаря и снаряжения: 1 lb (фунт) ≈ 0.45 кг.
  - Мастер в повествовании и ответах не использует слова «футы» и «фунты», всегда указывая расстояния в метрах (м) и вес в килограммах (кг).
- **Выбор единиц измерения при создании кампании**:
  - При создании кампании (через диалог с мастером, нулевую сессию или параметры `gameSettings.unitSystem`) создателю стола **всегда предоставляется выбор единиц измерения**: **Метрические (м, кг)** [по умолчанию] либо **Имперские (фт, фнт)**.
  - Если пользователь явно не указал иное, кампания создаётся строго с метрами и килограммами как основа (`unitSystem: "metric"`).

## 3. Протокол взаимодействия через MCP (`odm_narrator`)

Инструмент `odm_narrator` (или вызовы `/api/internal/mcp` с Bearer-токеном)
поддерживает операции, перечисленные в
`mcp/narrator-schema.mjs`, а поля engine actions — в `narrator.catalog`.

### 3.1. `connect` — Подключение к кампании
Запрашивает начальное состояние и проверяет готовность кампании.
```json
{ "action": "narrator.connect", "params": { "campaignId": "<id>" } }
```

### 3.2. `read` — Чтение стрима событий стола
Возвращает `currentSeq`, события, листы персонажей (`sheets`), участников (`members`), открытые броски (`pendingRolls`), недавние сообщения и вопросы из панели Ask (`asks`).
- **Бюджет размера (`maxBytes`)**: в кампаниях с 4+ прокачанными персонажами размер превышает 64 КБ (`ReadBudgetError`). Передавай **`projection: "live"`** и **`maxBytes: 131072`** (до 128 КБ) для быстрого чтения без пагинации:
```json
{ "action": "narrator.read", "params": { "campaignId": "<id>", "projection": "live", "maxBytes": 131072, "afterSeq": 0 } }
```

### 3.3. `catalog` — Просмотр 40+ серверных действий правил
Возвращает список доступных механик движка правил (атаки, заклинания, перемещение, отдых, инвентарь).
```json
{ "action": "narrator.catalog", "params": { "campaignId": "<id>" } }
```

### 3.4. `invoke` — Вызов действия движка правил
Требует `expectedSeq`, равный текущему `currentSeq` из `read`.
- **Запрос броска костей (`request_roll`)**:
  ```json
  {
    "action": "narrator.invoke",
    "params": {
      "campaignId": "<id>",
      "expectedSeq": 10,
      "name": "request_roll",
      "args": {
        "characterId": "<id>",
        "kind": "skill_check",
        "skill": "stealth",
        "dc": 14,
        "advantage": "none",
        "reason": "Попытка прокрасться мимо часового"
      }
    }
  }
  ```
- **Старт боя (`start_encounter`)**:
  ```json
  {
    "action": "narrator.invoke",
    "params": {
      "campaignId": "<id>",
      "expectedSeq": 11,
      "name": "start_encounter",
      "args": { "enemies": "goblin", "surprised": "enemies", "summary": "Засада в ущелье!" }
    }
  }
  ```
- **Перемещение токена (`move_token`)**:
  ```json
  {
    "action": "narrator.invoke",
    "params": {
      "campaignId": "<id>",
      "expectedSeq": 12,
      "name": "move_token",
      "args": { "tokenName": "Торин", "x": 5, "y": 8, "forced": true }
    }
  }
  ```
- **Атака персонажа (`pc_attack`)**:
  *Важно:* передавай ОБА поля: `enemyId` и `targetEnemyId` с одинаковым ID цели.
  ```json
  {
    "action": "narrator.invoke",
    "params": {
      "campaignId": "<id>",
      "expectedSeq": 13,
      "name": "pc_attack",
      "args": { "characterId": "<id>", "enemyId": "<enemy_id>", "targetEnemyId": "<enemy_id>", "weapon": "Длинный меч" }
    }
  }
  ```
- **Нанесение урона / добивание (`damage_enemy`)**:
  ```json
  {
    "action": "narrator.invoke",
    "params": {
      "campaignId": "<id>",
      "expectedSeq": 14,
      "name": "damage_enemy",
      "args": { "enemyId": "<enemy_id>", "amount": 8, "type": "slashing" }
    }
  }
  ```
- **Выдача лута в инвентарь (`grant_item`)**:
  ```json
  {
    "action": "narrator.invoke",
    "params": {
      "campaignId": "<id>",
      "expectedSeq": 15,
      "name": "grant_item",
      "args": { "characterId": "<id>", "name": "Зелье лечения", "qty": 1 }
    }
  }
  ```
- **Изменение золота (`modify_gold`)**:
  *Важно:* параметр называется **`delta`** (число со знаком), а НЕ `amount`!
  ```json
  {
    "action": "narrator.invoke",
    "params": {
      "campaignId": "<id>",
      "expectedSeq": 16,
      "name": "modify_gold",
      "args": { "characterId": "<id>", "delta": 25, "reason": "Добыча с поверженного архиерея" }
    }
  }
  ```
- **Трата ресурсов (`use_resource`)**:
  *Важно:* для `bardic_inspiration` цель `targetCharacterId` обязана быть другим персонажем (RAW 5e: бард не может вдохновлять себя).
  ```json
  {
    "action": "narrator.invoke",
    "params": {
      "campaignId": "<id>",
      "expectedSeq": 17,
      "name": "use_resource",
      "args": { "characterId": "<id>", "resource": "bardic_inspiration", "targetCharacterId": "<other_char_id>", "reason": "Вдохновение перед ударом" }
    }
  }
  ```
- **Начисление опыта (`award_xp`)**:
  ```json
  {
    "action": "narrator.invoke",
    "params": {
      "campaignId": "<id>",
      "expectedSeq": 18,
      "name": "award_xp",
      "args": { "characterIds": ["<id1>", "<id2>"], "amount": 500, "reason": "Победа над боссом" }
    }
  }
  ```

### 3.5. `narrate` — Публикация повествования в чат стола
```json
{
  "action": "narrator.narrate",
  "params": {
    "campaignId": "<id>",
    "expectedSeq": 19,
    "content": "Тяжелый удар рассекает кольчугу разбойника, и тот падает на каменный пол..."
  }
}
```

### 3.6. `delete_message` — Удаление сообщения из transcript
Удаляет точное `messageId` с актуальными `expectedSeq`, `timelineEpoch` и
сохранённым `commandId`. Это не rewind: механические эффекты и audit сохраняются.

### 3.7. `answer_ask` — Ответ на вопрос в панели «Спросите Мастера»
Приватные вопросы игроков **не записываются** в `campaign_events` (P2 privacy). Они приходят в `narrator.read` в массиве `result.asks[]` со статусом `"pending"`. Мастер отвечает на вопрос:
```json
{
  "action": "narrator.answer_ask",
  "params": {
    "campaignId": "<id>",
    "askId": "<ask_id>",
    "expectedVersion": 0,
    "answer": "Скрытная атака плута срабатывает 1 раз в ход при наличии преимущества..."
  }
}
```
Ответ сразу появляется в панели игрока без продвижения времени, хода или блокировки стола.

### 3.8. `release_floor` — Передача инициативы игрокам
Снимает только `hold`, восстанавливая сохранённый `hold.next`; не открывает и не
пропускает инициативу.

### 3.9. `snapshot` — Компактный orchestration snapshot
Возвращает выбранные секции `party/combat/location/recent/memory/npcs` для host.
Это чтение, не замена обязательному дочитыванию story cursor через `read`.

### 3.10. `edit_message` / `delete_message` — Правка истории стола
Обе операции требуют `campaignId`, точный `messageId`, актуальный `expectedSeq`,
сохранённый UUID `commandId` и `timelineEpoch`. `edit_message` дополнительно
принимает `content`, сохраняет автора и все маркеры `[roll:...]`.
`delete_message` удаляет запись основного чата и производные pin/beat.
Они не откатывают кости, HP, инвентарь, приватные Ask/whispers или аудит;
после правки перечитай `narrator.read`, а механику исправляй отдельной
разрешённой операцией движка либо явным откатом.

### 3.11. Общий и очередной ход
Через MCP `set_floor` выбирает `mode: "open" | "hold" | "spotlight"` (для
spotlight нужны `characterIds` игроков). `request_response` требует текущий
`expectedSeq`; в общем ходе укажите точный `roundNumber`, а в очередном
не указывайте его. Обе записи сохраняют `commandId` и `timelineEpoch` и
требуют перечитать состояние после подтверждения.
`gameSettings.globalTurn.enabled=true` включает общий ход. Лидер кнопкой
«Ответить сейчас» может досрочно закрыть активный раунд; сервер выдаёт
`global_turn_ready`, после чего внешний ведущий разрешает всю пачку и
подтверждённым `narrate(completeGlobalRound)` открывает следующий раунд.
При включении общего хода через MCP сервер сначала закрывает ввод и выдаёт
`global_turn_narrator_trigger`; до подтверждённого вступительного нарратива
игроки не ходят. Ручной `set_floor`/`release_floor` в небою здесь запрещён.
В обычном режиме лидер выбирает игроков через spotlight и тем же контролом
создаёт `lead_response_requested`: host отвечает на уже собранные реплики
раньше более поздних. Публичное указание Direct также будит ведущего;
если выбрано несколько игроков, host ждёт их ответы и разрешает общую пачку
после `spotlight_ready`; раннее снятие spotlight лидером передаёт уже
полученные ответы, не теряя их.
Приватное one-turn указание попадает только в аутентифицированный referee read.
Ни один из этих контролов не обходит pending roll или инициативу.
Автопилот включает сам игрок, лидер может выключить его; в очередном режиме
давший согласие игрок действует через `autopilot_action` после выбора spotlight.

### 3.12. `autopilot_action` — Действие opt-in игрока
Доступно в активной фазе global-turn и в выбранном spotlight очередного режима,
но не в боевой инициативе. Требует точные `characterId`, `expectedSeq`,
`timelineEpoch` и сохранённый `commandId`; `roundNumber` обязателен в общем ходе.
Сервер повторно проверяет opt-in, skip/mute/floor и отсутствие хода.

### 3.13. `finish_global_round` — Spatial finalizer без прозы
Используется host только после отдельных `location_narrate` для всех затронутых
комнат. В обычном чате раунд атомарно закрывает `narrate(completeGlobalRound)`.

### 3.14. Статус и операторское управление кампанией

- **Не объявляй «метода нет» по одному `narrator.catalog`: это только игровые
  действия движка.** По прямому заданию оператора проверь
  `odm_server(operation: "capabilities")` с текущим credential и схемы операторских
  tools; если tool не загружен, сначала найди его через discovery.
- Запуск из лобби уже есть: `odm_campaigns(operation: "set_status", campaignId,
  status: "active")`. Сначала прочитай кампанию через `get`; уже активную повторно
  не запускай. После подтверждённого статуса дочитай `narrator.read` и публикуй сцену.
- Редактирование основных полей: `odm_campaigns(operation: "update", ...)`;
  настроек: `odm_campaign_settings`; сцены, квестов и плана: `odm_story`.
  Точные операции и аргументы бери из актуальной схемы.
- Ошибка `External narrator writes require an active campaign` означает
  неактивный статус (например, `lobby`), а не отсутствие запуска. `start_scene`
  и `start_encounter` кампанию не активируют. Добавлять новый MCP-метод нужно
  только после проверки отсутствия
  существующего. При отказе прав сообщи ограничение credential, не обходи его:
  игровой payload не разрешает операторские действия или смену токена.

По окончании приключения статус переводится в завершённый:
```json
{ "action": "campaigns.set_status", "params": { "campaignId": "<id>", "status": "ended" } }
```

## 4. Режимы реплик игроков и фильтрация OOC

В чате игры игроки пишут сообщения в 4 режимах:
- **Do (Действие)** — янтарная плашка `⚔️ Действие`. Содержит поступок, реплику персонажа или оба сразу; это единственный игровой ход.
- **OOC (Вне игры)** — серый пунктир `👥 Вне игры`. Начинается с `(ooc)`. Автоматически отфильтровывается на уровне MCP, чтобы не отвлекать ИИ.
- **Direct / Lead** — высокоуровневые указания от лидера отряда внешнему ведущему.

## 5. Непрерывный игровой цикл (Live Reactive Loop)

Для непрерывной реакции должен работать внешний MCP-клиент (например,
OpenCode), который читает события и вызывает инструменты Мастера. Один только
MCP endpoint или `watch-player.sh` не запускает генерацию. Необязательный
`narrator/run.mjs` — вариант автоматизации внешнего клиента с явно настроенными
адаптером модели и supervisor, а не компонент сервера ODM. Подробности —
`docs/narrator-orchestration.md`. При ведении через MCP `watch-player.sh`
остаётся ускорителем:

```bash
ssh root@api.iroslyakov.com "/opt/odm/tools/watch-player.sh <LAST_PROCESSED_PLAYER_SEQ> <CAMPAIGN_ID>"
```

### КРИТИЧЕСКОЕ ПРАВИЛО ПЕРЕДАЧИ ПОСЛЕДОВАТЕЛЬНОСТИ:
> Передавай в `watch-player.sh` номер **последней фактически обработанной реплики игрока**, а **НЕ** `currentSeq` после твоих административных команд (`release_floor`, `grant_item`, `modify_gold` и т.д.)!
> Иначе, если игрок отправил реплику в браузере прямо во время выполнения твоей пачки команд, его сообщение получит `seq` меньше финального `currentSeq`, и слушатель его безвозвратно пропустит!

1. Скрипт ждёт появления новых игровых ходов (Do), приказов Director, вопросов Ask или запрошенных бросков.
2. Игнорирует оффтоп `(ooc)`.
3. При появлении активности завершается с кодом 0 и выводит:
   - `LATEST_SEQ: <seq>`
   - `[<seq>] player: <сообщение>`
   - `ASK [<id>] (<scope>): <вопрос>`
   - `PENDING_ROLL [<id>] char=<id> kind=<kind>: <reason>`
4. Модель просыпается, считывает контекст через `narrator.read` (`projection: "live"`, `maxBytes: 131072`), делает броски/урон (`invoke`), публикует ответ (`narrate`), передаёт ход (`release_floor`) и снова ставит слушатель в фон.

`watch-player.sh` — только ускоритель: после пробуждения authoritative `read`
самостоятельно дочитывает story и Ask. Все показанные записи иллюстративны; для
каждой записи сохраняйте UUID `commandId`, полный payload, последний cursor и
`timelineEpoch`, перечитывайте после неё и не повторяйте неоднозначный результат
иначе чем один раз тем же payload/commandId.

## 6. Отыгрыш персонажа-сопартийца ИИ-Мастером (Party Member / Companion Bot)

Если оператор стола просит ИИ параллельно с ведением игры отыгрывать конкретного героя отряда (например, гуся Игната / `White_Goose`):
1. **Не смешивай речь персонажа с нарративом мастера**: реплики и действия персонажа должны появляться в общем чате стола от его собственного имени (плашка Действия или Речи).
2. **Аутентификация игрока через токен (только оператор вне narrator):**
   - Сессионный токен выпускает отдельно авторизованный оператор. Ведущий не
     mint'ит токены, не читает auth DB и не получает право имперсонации игрока.
3. **Отправка хода игрока (операторская предварительная настройка):**
   - Отправляй действие персонажа через стандартный endpoint:
     ```bash
     curl -s -H "Authorization: Bearer <PLAYER_TOKEN>" -H "Content-Type: application/json" \
       -d '{"content": "*Снимаю лук и целюсь в колокол.* ХОНК.", "kind": "do"}' \
       http://127.0.0.1:3005/api/campaigns/<campaign_id>/actions
     ```
   - Запрос создаст стандартное событие `message_added` с `authorType: "player"` и `characterId`.
4. **Разрешение Мастером**:
   - После публикации хода персонажа перечитай состояние стола (`narrator.read`), выполни необходимые механические броски/урон через `narrator.invoke` и опубликуй реакцию мира через `narrator.narrate`.
