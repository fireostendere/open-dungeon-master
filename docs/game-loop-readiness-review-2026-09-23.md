# Готовность игрового цикла через MCP — ревью 2026-09-23

Целевая модель: **игроки ходят через браузер, MCP — только доверенный пульт
оператора и внешнего ГМа**. Персональный MCP игроков не требуется. Модель
работает во внешнем MCP-клиенте, а не на сервере ODM. Отсутствие `narrator-host`
или серверной модели **не является дефектом и не блокирует этот режим**.
Базовый цикл «браузерный игрок → правила/кости сервера → операторский MCP →
ответ Мастера» подтверждён на production-релизе `756971f`. Непрерывную сессию
внешней модели с восстановлением cursor после перезапуска на production ещё
нужно проверить отдельно; модель на сервере для этого не требуется.

## Проверенный путь

| Звено | Состояние после изменений | Граница |
| --- | --- | --- |
| Создать стол, участников, листы, технического DM | Операторские MCP tools; добавлен `campaigns.assign_dm_seat` | Создание/выдача персональных учётных данных остаётся отдельной auth-операцией |
| Принять действия людей | Браузер/REST `/actions` с личной сессией; общий ход и spotlight проверяются сервером | Это намеренная граница: операторский MCP не имперсонирует игрока |
| Услышать стол | Внешний MCP-клиент читает durable story/Ask через `read`/`snapshot`; `watch-player.sh` — необязательный ускоритель | Для непрерывной реакции внешний клиент должен оставаться запущенным; серверная модель не нужна |
| Разрешить действия | `odm_narrator.read/catalog/invoke`, серверные кости, pending roll, encounter/initiative | Никакого текстового «успеха» до результата движка; host не заменяет движок |
| Выбрать темп/очерёдность | Лидерский UI и MCP `set_floor`, `request_response`; глобальный barrier или пакет `spotlight_ready` | В бою и при pending roll принудительный ответ/смена пола запрещены |
| Отыграть автопилот | Изолированный actor, `autopilot_action`, повторная проверка согласия, mute/skip/floor | Только явный self opt-in; боевую инициативу автопилот не имперсонирует |
| Исправить историю | MCP `edit_message`/`delete_message` с CAS, receipt и пересборкой очереди/памяти | Не откатывает HP/кости/инвентарь; для механики нужна отдельная команда или rollback |

## Существенные находки

1. **Production-развёртывание подтверждено.** `odmctl status` и
   `odm-mcpctl status` показывают `ready` и одинаковый SHA `756971f`; HTTP
   `/api/ready` вернул `{"ok":true}`. Перед переключением создан зашифрованный
   снимок `0c5aa341`, предыдущий рабочий релиз сохранён для отката.
   Отсутствие narrator-контейнера ожидаемо для внешнего MCP-ГМа. Внешнему
   клиенту нужны авторизованный MCP-доступ, сохранённый cursor последней
   обработанной реплики игрока и повторный `read` после записи;
   `watch-player.sh` не источник истины.
2. **Production HTTP/MCP E2E подтверждён.** На объединённой версии
   `next build --webpack`, Docker production build и локальный E2E прошли.
   Тот же скрипт на production проверил двух игроков с bearer-сессиями,
   технический DM seat, отказ игроку в операторском MCP, Do (включая речь), приватный
   Ask, серверный бросок, MCP narration/edit/delete, общий раунд и автопилот.
   Созданные тестовые кампания и аккаунты удалены скриптом после проверки.
   Дополнительно GPT-6 D&D Edition выполнил один ход на одноразовой локальной
   кампании через настоящий MCP/SQLite: `connect` → `read` → `snapshot` →
   `request_roll` → `narrate` (91,7 с, 8 вызовов tools). Сервер вернул
   Perception 23 против DC 12, повествование не выдумало иной результат;
   `floor` был открыт, поэтому `release_floor` не требовался. Первый вызов
   `snapshot` ошибочно содержал `projection`; агент исправил параметры и
   продолжил без повторного броска. Многопользовательский production-сценарий
   с **живой внешней моделью** и recovery её cursor ещё не проверен: HTTP E2E
   использовал детерминированный MCP-клиент, не модель.
3. **P1 — коррекция текста не является revision history.** Актуальные
   сообщение/память/очередь синхронизируются, ID и seq события сохраняются,
   но старый текст после `edit_message` не хранится как отдельная
   административная версия. Для юридически значимого аудита нужна отдельная
   защищённая история правок; удалённые сообщения не должны всплывать в
   обычном narrator read. Dice и moderation reports остаются отдельно.
4. **P1 — лидер выше DM по управлению сюжетом, не по правилам.** Лидер может
   назначить DM seat, задать приватную one-turn директиву, выбрать spotlight,
   запустить ответ или досрочно запечатать глобальный раунд. Директива и
   событие ответа имеют приоритет в host. Но engine, initiative, приватность
   других игроков и безопасность не отменяются. Между конкурентными
   назначениями floor лидером и DM действует последний подтверждённый write;
   жёсткого отдельного «замка лидера» нет.
5. **P1 — нет offsite backup.** Снимок `45692cba` прошёл `odmctl
   restore-check --yes` 2026-09-23 в изолированном месте: целостность SQLite
   подтверждена, живое состояние не затронуто. Новый pre-update snapshot
   `0c5aa341` создан успешно. Удалённой копии по-прежнему нет.
6. **P1 — внешний D&D-роутер требует отдельного эксплуатационного smoke.**
   Luna-first Auto и ограниченный Sol-маршрут слиты в `custom_opencode/main`
   через PR #62, все обязательные проверки того репозитория прошли. Но
   установленный внешний процесс после слияния не перезапускался и фактический
   маршрут оплаченного production-хода не логировался. Это не серверная
   модель ODM и не часть его deploy.
7. **P1 — GitHub CI ODM не стартовал.** Все jobs PR #44 отклонены до первого
   шага из-за ограничения биллинга GitHub Actions. Это не результат тестов;
   локальные и production-проверки перечислены ниже.
8. **P2 — зависимости требуют отдельного аудита.** `npm ci` внутри production
   Docker build сообщил о 5 уязвимостях (1 moderate, 4 high). В этом цикле
   транзитивные зависимости не обновлялись и влияние на runtime не оценивалось.

## Что именно изменено

- Открыты и проверены MCP `edit_message`, `delete_message`, `set_floor`,
  `request_response`, `finish_global_round`, `autopilot_action` и назначение
  технического DM seat. Последовательные записи требуют актуальный seq;
  `commandId`/epoch и receipt защищают от двойной записи при timeout.
- Включение общего хода через MCP теперь ставит тот же серверный барьер, что
  и браузерная настройка, и публикует обновление для клиентов. Ручное
  управление небойным floor не может сломать активный глобальный раунд.
- Необязательный внешний host обрабатывает `lead_response_requested` раньше более поздних реплик,
  передаёт приватную директиву только referee, пересобирает текущую пачку при
  редактировании и чистит compacted memory после удаления.
- Лидерский UI получил немедленный ответ и видимый roster автопилотов.
  Последовательный spotlight блокирует повторный ход уже ответившего игрока.
  После ответов всех выбранных игроков host разрешает одну пачку, а не
  отдельные реплики; раннее освобождение пола передаёт частичную пачку.
  Автопилот может отыграть согласившегося игрока и вне общего хода.
- Docker host (`narrator/Dockerfile`) — опциональный вариант размещения
  внешнего клиента, не серверная обязанность ODM и не release gate MCP-режима.

## Проверки и release gate

Пройдены: полный `npm test` (266 suites), `tsc --noEmit`, `next build --webpack`,
Docker production build, локальный и production HTTP E2E (по 4 сценария),
54 Python-теста deploy-контроллера, контрактные тесты D&D-роутера и один
реальный GPT-6 D&D Edition ход через локальный MCP. Production E2E создал и
удалил только отдельную тестовую кампанию и тестовых игроков; живые кампании
не менялись. Проверка нового Dockerfile через `docker buildx build --check`
прошла на сервере. При переходе со старого deploy-контроллера обновление
пришлось запустить прямо из релизного source: установленный контроллер до
переключения восстанавливал старый путь `deploy/Dockerfile`.

Статус — **базовый игровой цикл через операторский MCP подтверждён на
production**. Для полностью автономного режима требуется отдельно держать
внешнего ГМа запущенным и проверить восстановление его cursor после рестарта;
это не обязанность ODM-сервера. Также остаются offsite backup и недоступный
из-за биллинга GitHub CI. Личный MCP gateway игроков и модель на сервере в
целевую архитектуру не входят.
