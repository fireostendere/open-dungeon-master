# Эксплуатация и обновления

Команды Linux: `sudo odmctl …`. Windows: `%LOCALAPPDATA%\OpenDungeonMaster\odmctl.cmd …`.
Операции выполняются на машине установки. Для SSH не требуется особый agent:
запустите тот же CLI после подключения.

| Команда | Назначение |
|---|---|
| `status` | Readiness, commit, свободный диск, возраст backup, последний restore drill |
| `start` / `stop` | Запуск / намеренная остановка; watchdog не отменяет намеренный stop |
| `logs` | Последние 200 строк контейнерных журналов |
| `check-update` | Получить сведения о новой версии без установки |
| `update` / `update --ref COMMIT` | Отдельная сборка, probe-тесты, snapshot, переключение с откатом |
| `rollback --yes` | Предыдущая версия вместе с предобновлённой БД; более новые ходы откатываются |
| `backup` / `snapshots` | Создать шифрованный snapshot / показать snapshots |
| `restore-check latest` | Восстановить во временную папку и проверить шифрованную SQLite, не трогая live |
| `restore ID --yes` | Восстановить реальную БД, media и provider state |
| `check` | Проверка restic и retention обычных ежедневных snapshots |
| `assets` / `model` | Повторить установку контента / выбранной локальной модели |
| `auth …` | Команды единого визарда внутри контейнера |
| `recovery-kit` | Создать секретный ZIP с ключами восстановления для хранения вне сервера |

## Как обновление защищает данные

Upstream image не используется. Контроллер получает выбранную ветку приватного
форка, создаёт отдельный Git worktree конкретного коммита и собирает образ.
Текущий сервер продолжает работать во время сборки. В новом образе запускаются
быстрые provider-тесты; сохраняется immutable Docker image ID.

После успешной сборки приложение останавливается и создаётся согласованный
restic snapshot. В нём находятся SQLite, WAL при наличии, картинки и ключи.
Затем запускается кандидат. Успех определяется `/api/ready`, который открывает
реальную шифрованную БД, а не только отдаёт HTTP 200.

Если кандидат не готов, возвращаются **и образ, и снимок БД до миграции**.
Недостаточно запустить старый JavaScript поверх уже изменённой схемы.
`config/transaction.json` позволяет восстановиться при следующем запуске после
оборванного обновления/восстановления. Операции сериализуются файловой блокировкой:
backup, updater и watchdog не меняют состояние одновременно.

Откат возвращает игру к сохранённому моменту. Операционные окна должны быть вне
сессии. Полной распределённой HA/zero-downtime системы здесь нет: приложение
архитектурно однопроцессное. Старые `state-before-restore-*` сохраняются для ручной
проверки, а не стираются автоматически. После успешного восстановления и отдельного
бэкапа их можно удалить вручную, проверив путь. Старые images/worktrees также не
удаляются глобальным Docker prune: это могло бы уничтожить ресурсы других проектов.

## Расписание по умолчанию

Время — локальное время ОС сервера, не timezone браузера. Linux: watchdog каждую
минуту, backup 03:30 ежедневно, restic check/retention в воскресенье 04:15,
restore-drill 1-го числа 05:00, проверка обновлений ежедневно 05:30.
Windows: аналогичные задачи, restore-drill по воскресеньям. Пропущенные задачи
могут запускаться после включения компьютера.

Автообновление включается только флагом установщика. Без него расписание только
проверяет наличие новых коммитов. Для изменения часов используйте соответствующий
systemd timer override или Windows Task Scheduler. Не редактируйте чужие задачи.
Имена Linux units начинаются с `odm-<hash пути>`; Windows tasks — `ODM-<port>-`.

## Мониторинг

`/api/health` остаётся существующим liveness/диагностическим интерфейсом.
`/api/ready` — минимальный web+DB readiness без названий кампаний или ключей.
Отказ LLM-провайдера не должен вызывать бесконечные рестарты исправной SQLite.
Watchdog ограничивает рестарты: максимум три за час, минимум десять минут между
попытками. Низкое место на диске, backup или off-site старше 26 часов создают alert.

Состояние: `logs/health.json`; последняя тревога: `logs/last-alert.json`.
Ошибки внешних программ сохраняются локально в защищённом
`logs/last-command-error.log`, а не публикуются в health API.

HTTPS webhook для тревог задаётся без URL-секрета в аргументах:

```bash
sudo odmctl alerts-config --url-stdin
```

Введите URL и EOF. При конфигурации отправляется тестовая тревога. Это webhook с
JSON `{at, kind, message}`; принимающая сторона должна поддерживать такой формат.
Без внешнего адреса события остаются локальными. Для обнаружения полного падения
сервера/провайдера сети нужен **внешний** монитор, проверяющий ваш HTTPS `/api/ready`.
Watchdog на отключённом сервере физически не может отправить уведомление.

## Что не меняется автоматически

Firewall, SSH, GPU-драйверы, питание/сон Windows, DNS, аккаунты LLM и другие
проекты. Docker daemon не открывается по TCP. Ollama не публикуется наружу.
Конфликт занятого порта или невозможность поднять runtime — ошибка с сохранением
данных, а не повод убивать чужой процесс.
