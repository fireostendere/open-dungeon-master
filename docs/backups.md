# Бэкапы и восстановление

## Что сохраняется

`state/data` — шифрованная SQLite со всеми таблицами: персонажи, кампании,
сообщения, листы, игровые настройки, NPC, журналы и остальные данные приложения.
`state/uploads`, `generated`, `audio` — файлы, на которые ссылается БД.
`state/provider-auth` — отдельное состояние входа Codex, не чужой профиль OpenCode.
`config/app.env` — ключ шифрования БД и runtime-настройки.
`config/install.json`, `recovery.json`, `admin.json` — метаданные восстановления.

Все эти файлы сохраняются в **шифрованный restic-репозиторий** `backups`.
В момент снимка приложение остановлено, поэтому SQLite/WAL, media и авторизация
не копируются в разные моменты при продолжающейся записи. Сервис возобновляется
после локального snapshot; передача off-site не держит его остановленным.

Не сохраняются GitHub token, Git worktrees, Docker images, скачиваемые веса Ollama
и embedding cache. Их можно получить заново. Ключ restic не хранится только
внутри зашифрованного им snapshot: это сделало бы восстановление невозможным.

## Два разных ключа

Ключ SQLite хранится в `config/app.env` (для старых upstream установок — также
возможен `data/.db-key`). Он входит в зашифрованный snapshot.
Пароль restic находится в `config/backup.password`. **Сохраните его отдельно от
машины**. Потеря пароля restic делает бэкап бесполезным; потеря ключа SQLite делает
саму игровую базу нечитаемой. Ни один ключ не должен попадать в issue, лог или чат.

```bash
sudo odmctl recovery-kit
```

Команда создаёт ZIP в `config/` с паролями и параметрами восстановления. Это
**секретный, сам по себе не зашифрованный** комплект: храните его в password manager
или на зашифрованном внешнем носителе. Он не заменяет игровые restic snapshots.

## Проверить бэкап сейчас

```bash
sudo odmctl backup
sudo odmctl snapshots
sudo odmctl restore-check latest
```

`restore-check` извлекает snapshot во временную папку, запускает
проверку шифрованной БД правильным ключом и проверяет наличие игровых таблиц.
Текущие кампании не заменяются. Результат записывается в `config/last-restore-check.json`.

## Восстановить игру

```bash
sudo odmctl restore SNAPSHOT_ID --yes
```

Перед заменой создаётся ещё один snapshot текущего состояния. Восстановление
проверяется до переключения; предыдущая папка состояния сохраняется как
`state-before-restore-*`. Берётся версия приложения из recovery manifest, а не
произвольная новая версия поверх старого snapshot. При отсутствии локального
образа нужный коммит собирается из репозитория.

После переноса на другой домен проверьте `APP_PUBLIC_URL` и `ODM_PUBLIC_ORIGIN` в
`config/app.env`: восстановление возвращает runtime-настройки старого сервера.
Обновите оба адреса осознанно и выполните `odmctl start`.

## Off-site: другой диск, SFTP, S3 или совместимое хранилище

Локальный backup на том же диске защищает от неудачного обновления, но не от
отказа диска, удаления VPS или ransomware с доступом root. Нужна отдельная копия.
Контроллер использует `restic copy`; сначала завершается локальный snapshot,
затем копируется в другой шифрованный репозиторий.

```bash
sudo odmctl remote-config /mnt/external-disk/odm-backups --password-file /root/secrets/offsite.password
# Только для НОВОГО пустого репозитория:
sudo odmctl remote-init
sudo odmctl offsite
sudo odmctl restore-check latest --remote
```

Для S3 вместо пути задайте `s3:https://s3.example.com/bucket/odm`.
`--credentials-file /root/secrets/s3.json` принимает JSON с
`AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, при необходимости
`AWS_SESSION_TOKEN` и `AWS_DEFAULT_REGION`. Поддерживаются также документированные
в контроллере B2/Azure credential-поля. Файл не исполняется как shell-код.
Для SFTP используйте `sftp:user@host:/path`; заранее настройте SSH-доступ и
проверенный host key под пользователем запуска контроллера.

`remote-init` нельзя использовать как универсальное лечение ошибки доступа к
существующему репозиторию. Для существующего off-site достаточно `remote-config`
и правильного пароля. Копирование завершается с ошибкой при неверном ключе,
не пересоздавая старые backups.

Обычные scheduled snapshots: 7 ежедневных, 4 недельных, 6 месячных.
Предобновлённые и pre-restore snapshots автоматически этой политикой не удаляются;
они нужны для отката. Следите за ростом и удаляйте заведомо лишние только после
проверки `previous.json` и отдельной удалённой копии. Удалённые snapshots также
не prune-ятся молча.

## Полная потеря сервера

1. Поднимите новую машину тем же installer и своим GitHub-доступом.
2. Настройте `remote-config` для **существующего** off-site с паролем из recovery kit.
   Не запускайте `remote-init` поверх него.
3. Выполните `restore-check SNAPSHOT_ID --remote`, затем
   `restore SNAPSHOT_ID --remote --yes`.
4. Проверьте домен, вход, сохранённую кампанию и свежий off-site backup.

Для локальной копии на внешнем носителе её можно подключить как remote path и
пройти ту же процедуру. Это избегает замены пустого свежего `backups` вручную.

## Ручные старые установки

Установщик никогда не забирает чужую БД из текущего проекта автоматически.
Перед переносом остановите старое приложение, сохраните его SQLite/WAL вместе
с правильным ключом и всеми ссылочными media. Не импортируйте одну `.sqlite` без
ключа и не запускайте две версии приложения над одной базой. Управляемый restic
restore принимает только snapshots с recovery manifest; произвольный архив папки
нельзя выдавать за проверенный совместимый snapshot.
