# Первый внешний сеанс: технический сценарий P2

Статус: инструкция для контролируемого плейтеста, не журнал пройденной приёмки.
В репозитории есть управляемый long-lived host `narrator/run.mjs` и
`deploy/narratorctl.py`. Обычный чат или чтение MCP resource всё равно не
запускают непрерывный цикл сами: оператор должен явно запустить narrator-host и
настроить его adapter/credential.

## Подготовка оператора

Используйте отдельную тестовую кампанию и проверенный backup, не единственную
копию игры. Подготовьте ведущего, двух обычных игроков, приглашения и листы.
Кампания должна быть active, `dmMode:human`, с DM seat, без AI cover, TTS и
автоматических карт. Внешняя LLM играет ведущего, поэтому human здесь обозначает
отключение внутреннего AI-цикла, а не запрет внешней модели.

До начала оператор проверяет `gameSettings.combatMode`: `classical` по умолчанию
или явно выбранный `jrpg`. В JRPG в текущей встрече цели не блокируют дальность,
LOS, укрытие и opportunity attacks; сервер всё так же применяет инициативу,
действия, кости, ресурсы, HP, состояния и приватность. Не трактуйте режим как
объединение разных комнат/встреч или автоматические Sneak Attack, Pack Tactics
либо flanking.

Настройка restricted sidecar описана в [dm-player-boundary](dm-player-boundary.md).
Оператор выбирает именно его HTTPS/private-tunnel endpoint. Не передавайте
операторский bearer модели или игрокам. Проверьте `odm_server capabilities`:
роль narrator, нужный campaignId и ограниченный набор действий. Наличие токена
в конфигурации приложения само по себе не перенастраивает operator sidecar.

Установите локальную каноническую policy в trusted instructions отдельного
host без shell/Git/email. Проверяйте совместимый SDK, tools/resources discovery
и фактические вызовы; наличие поля в схеме не доказывает сквозную работу.

## Чтение и три независимых указателя

`odm_narrator` принимает `operation`, `campaignId` и параметры операции.
Для нового клиента вызывайте `connect(stateDelta:true)`: handshake возвращает
только `cursor.currentSeq` и `timelineEpoch`, без дублирования полного state.
Затем первый `read(stateDelta:true)` даёт полный baseline и revision; следующие
reads передают `knownStateRevision` и получают entity patch. Legacy `connect`
без этого флага сохраняет прежнюю форму `state`. Для больших ответов доступны
`paged:true`, `maxBytes` и `projection`.

Для read существуют три разных механизма, их нельзя смешивать:

1. **Сюжет:** `afterSeq` -> `nextCursor`, до `hasMore:false`. Даже пустая после
   OOC-фильтрации страница может требовать продолжения. Только полностью
   прочитанное currentSeq годится как expectedSeq следующей сюжетной записи.
2. **Снимок:** при `paged:true` собирайте entries в порядке offset/index;
   `nextPage` передавайте как `pageCursor`, сохраняя остальные параметры read.
   У всех страниц один hash. До complete нельзя подтверждать сюжетный курсор.
   При 409 от сменившегося снимка повторите чтение без pageCursor, не мутацию.
   Для реализации сборки есть `assembleReadPages` в `src/lib/mcp-read-budget.mjs`.
3. **Очередь Ask:** `afterAskSeq` -> `askQueue.nextCursor`, до
   `askQueue.hasMore:false`. После обработки начинайте следующий опрос с нуля,
   чтобы видеть всё ещё ожидающие заявки. Эта очередь не зависит от story seq.

Бюджет read по умолчанию 65 536 байт, допустимый диапазон 4 096..131 072.
Это бюджет JSON-данных снимка: фиксированная policy и MCP envelope добавляются
снаружи. Клиент должен учитывать их отдельно. Одиночное слишком большое
значение не обрезается и приводит к отказу 413. `projection:live` явно опускает
историю recentMessages/recentRolls/recentDmWhispers/chapters, но не новые
события/результаты. Используйте его только при уже сохранённой истории host;
сохраняйте результаты всех прочитанных страниц, не только последней.

## Ответы и подтверждения

Human-mode Ask возвращается как pending с локализованным подтверждением
передачи. Для `answer_ask` сохраняйте UUID commandId и весь запрос до отправки,
передавайте askId и version как expectedVersion. Успешный ответ даёт answered
и новую version. Точный повтор восстанавливает тот же ответ; другое содержание
или конкурирующий ответ получает 409. Для независимого Ask обычно не нужен
expectedSeq: его необязательная старая проверка всё ещё отвергает устаревший
сюжетный курсор. Не меняйте параметры неоднозначного повтора автоматически.

В репозитории `narrator/run.mjs` уже есть этот цикл: он начинает каждый новый
скан Ask с нулевого курсора, дочитывает все страницы, сохраняет незавершённую
команду и не прыгает вперёд по сюжету после ошибки. `watch-player.sh` — лишь
оптимизация пробуждения, а не обязательный listener.

Приватный Ask доступен автору и доверенному ведущему; member GET отдаёт только
свои private и общие table записи. Уведомления не содержат вопроса/ответа.
Whisper-ответ через send_whisper указывает точные replyToWhisperIds; не отмечайте
все сообщения автора, включая новые, автоматически.

После сюжетной команды используйте `readAfter` с текущим
`knownStateRevision`: подтверждённая команда вернёт authoritative post-commit
delta в той же MCP-команде. Отдельный network read нужен только для следующих
страниц/events или recovery. Не повторяйте урон, награду или end_turn по тексту
ответа. Narration сама не продвигает инициативу.
После narration проверьте hold и отдельной подтверждённой release_floor
откройте ответы, сохранив вложенный режим. Иначе игроки могут остаться на hold.
После физического броска перечитайте авторитетный roll_result; не бросайте
повторно и не считайте исчезновение pending доказательством конкретного числа.

## Модерация и ограничения

Минутные квоты: Ask 10, whisper 20, action 30 на пользователя/кампанию/канал;
дополнительно общий пользовательский предел 60 и кампанийный 300. Счётчики
хранятся в SQLite. Pending Ask: максимум 20 на пользователя и 500 на кампанию.
Это не суточный бюджет провайдера и не гарантия тематической безопасности.
Mute блокирует новые Ask/actions/whispers, но не чтение своей истории.
Смысловое поведение и приватность текста выбранной LLM проверяются отдельно.

## Приёмка двух игроков

Откройте две обычные браузерные сессии. Проверьте речь/действие/OOC и реальные
ресурсы; два боевых раунда с PC/противником/companion; один физический бросок;
три последовательных whisper-ответа; 25 Ask от двух пользователей с соблюдением
минутной квоты; перезапуск host; отключение/восстановление сети с backlog 501+.
Ни один private ответ, DM outline или credential не должен появиться у другого
игрока. Проверьте mute всех каналов и модельные случаи RU/EN/PL.

Для каждого результата запишите фактический commit, версии SDK/модели,
выполненный шаг, наблюдение и ограничения. После этого отдельно выполните
backup/restore SQLCipher с медиа и повторную сверку состояния. Непройденные
шаги остаются непроверенными. Эта ветка сама не выполняла ни развёртывание,
ни восстановление, ни проверку живой модели.
