# Быстрое создание кампании и персонажей ODM

Это операторский сценарий: прямой запрос разрешает названные записи, а не
посторонние изменения. Сохраняйте [общий контракт](../../../../docs/agent-skills.md#общий-контракт-и-границы).
Для player-originated payload сначала действует `odm-dm-policy`; этот сценарий
не переводит игрока в оператора и не заменяет протокол ведения.

## Одна подготовка на пакет

- Сохраните известные owner, title, уровень, сложность, режим, состав и файл.
  Используйте данные текущего запроса/уже подтверждённых ответов, не память о другом столе.
  Недостающие существенные выборы соберите одним вопросом. Без явного выбора
  предложите метры/кг и classical с возможностью выбрать imperial/JRPG;
  defaults применяются без дополнительной остановки на отдельную анкету.
- Загрузите только нужные MCP-схемы одним discovery/list. Имена tools зависят от
  хоста; аргументы ниже — для фактических `odm_*`. Повторная загрузка уже известных
  схем и навыков не ускоряет запись. У новых схем/credential проверку повторите.
- Один `odm_server(operation: capabilities)` на пакет с текущим credential;
  `status`, SSH, чтение исходников, build/deploy нужны только при реальном сбое
  или отдельно порученном изменении механики. Не переключайте токен после отказа.
- Одновременно можно прочитать `odm_campaigns.list` для проверки дубликата и
  `odm_characters.list(ownerUsername)` для каждого уникального владельца героев.
  Из полного ответа библиотеки сохраните `name/userId/id/level/sheet` выбранных
  героев; известный username не требует `odm_users`. При одинаковых именах
  уточните владельца/ID, не выбирайте случайный лист.

## Создание стола

1. Один `odm_campaigns.create`: передайте все известные поля, особенно
   `gameSettings`. `difficulty` (опасность), `dmDifficulty` (строгость) и
   `yolo21Enabled` (YOLO) — разные значения, каждое берётся из запроса.
   Пример формы аргументов, не готовый заказ или значения для всех кампаний:

   ```json
   {"tool":"odm_campaigns","arguments":{"operation":"create","ownerUsername":"<owner>","title":"<title>","startingLevel":3,"difficulty":"hard","maxPlayers":5,"gameSettings":{"unitSystem":"metric","combatMode":"classical","language":"ru","yolo21Enabled":true,"dmDifficulty":3,"dmMode":"human","ttsEnabled":false,"mapsEnabled":false,"targetParty":{"size":5,"level":3}}}}
   ```

   Для пустого стола достаточно owner/title; дополнительные настройки из примера
   нужны только по задаче. Ответ `create` содержит сохранённые `campaign` и
   `owner`: проверьте ID, title, owner, status и настройки здесь же, не вызывая `get`.
   Не считайте `status: active` частью create: запуск — отдельный `set_status`.
2. Если поручен сюжет, сохраните его коротко:
   `odm_campaign_settings(operation: story, patch: {world, style})`, затем
   `odm_story.set_scene`, `set_quest_log`, `set_outline`. Публичная сцена/квесты
   не содержат секретной разгадки; outline не раскрывайте в общем ответе.
   Награда пока обещана — не вызывает `grant_item`/`modify_gold`.
3. Если владелец играет PC и внешний AI должен вести, добавьте существующий
   технический DM-аккаунт через `odm_members.join`; возьмите `user.id` ответа
   и вызовите `odm_campaigns.assign_dm_seat(seat: dm, userId)` **до** листа PC
   владельца. DM не получает лист. Не угадывайте ID бота и не создавайте аккаунт.
4. Добавьте остальных владельцев выбранных героев через `odm_members.join`;
   owner уже член нового стола. Записи в один стол выполняйте последовательно,
   независимые чтения разных владельцев — параллельно. Ответ join даёт
   сохранённые campaign/user; отдельный users.get не нужен.

`odm_campaign_settings` не является чтением: не отправляйте пустой `patch: {}`
для просмотра defaults. При возобновлении/изменении существующего стола читайте
`odm_campaigns.get`, `odm_members.list` и `odm_sheets.list` один раз перед пакетом.

## Существующие герои

Не пересоздавайте найденных библиотечных героев и не копируйте HP/ресурсы из
другой активной кампании. После проверки членства выполните по одному вызову:

```json
{"tool":"odm_characters","arguments":{"operation":"instantiate","characterId":"11111111-1111-4111-8111-111111111111","campaignId":"22222222-2222-4222-8222-222222222222","targetLevel":3}}
```

UUID здесь условные: используйте фактические ID библиотеки и созданного стола.
`targetLevel` передавайте только для согласованного целевого уровня; без него
сервер использует startingLevel кампании. Ответ содержит живой `sheet`:
проверьте `campaignId`, `libraryCharacterId`, `userId`, уровень, HP/КД, классы,
портрет, заклинания и ресурсы. Библиотечный и кампанийный ID различаются.

Если герой требует правки до входа, сначала обновите его библиотечный шаблон по
[dnd-characters](../../dnd-characters/SKILL.md#обновление-старого-героя-и-homebrew),
потом инстанцируйте. Не переносите владение через `transfer`, когда нужна копия.
Один владелец может иметь один PC-лист на столе; конфликт не решается удалением.

## Новый персонаж

Следуйте [dnd-characters](../../dnd-characters/SKILL.md#быстрое-создание-персонажа-в-библиотеке-odm).
Создайте один валидный `sheet`, затем один `odm_characters.create` на героя.
`createSheetSchema` требует name/race/class/abilities/maxHp/ac/hitDice/proficiencies;
обычный новый билд передаёт `acOverride: false`, а каталог добавляет штатные черты.
Механические выборы и расовые ASI уже включены в показатели ровно один раз.
Homebrew требует явного согласованного правила и поддержанного ресурса движка,
а не только красивого текста в notes.

Пример минимального payload: заранее согласованный волшебник-человек 1-го уровня,
D&D 2014, стандартный массив с уже учтёнными +1 расы. Это образец структуры,
не выбор билда вместо оператора; замените владельца и имя, заполните согласованные
appearance/backstory и выборы. Скорость `30` хранится в единицах движка и
показывается столу как 9 м при metric.

```json
{
  "tool": "odm_characters",
  "arguments": {
    "operation": "create", "ownerUsername": "<owner>", "level": 1, "role": "pc",
    "sheet": {
      "name": "<name>", "race": "human", "class": "wizard", "background": "sage",
      "abilities": {"str": 9, "dex": 15, "con": 14, "int": 16, "wis": 13, "cha": 11},
      "maxHp": 8, "ac": 12, "acOverride": false, "speed": 30,
      "hitDice": {"die": "d6", "total": 1, "spent": 0},
      "proficiencies": {
        "saves": ["int", "wis"], "skills": ["arcana", "investigation", "history", "insight"],
        "languages": ["Common", "Elvish", "Draconic", "Dwarvish"], "tools": [], "armor": [],
        "weapons": ["daggers", "darts", "slings", "quarterstaffs", "light crossbows"]
      },
      "equipment": [{"name": "Dagger", "qty": 1, "equipped": true}, {"name": "Arcane Focus", "qty": 1}, {"name": "Scholar's Pack", "qty": 1}, {"name": "Spellbook", "qty": 1}],
      "spellcasting": {
        "ability": "int", "slots": {"1": {"max": 2, "used": 0}},
        "prepared": ["Mage Hand", "Prestidigitation", "Ray of Frost", "Mage Armor", "Magic Missile", "Shield", "Sleep"], "known": []
      },
      "notes": "D&D 2014, standard human; racial ASI included once. Spellbook also contains Alarm and Find Familiar; only four level-1 spells prepared."
    }
  }
}
```

## Картинка, завершение и продолжение

- Для переданной обложки/портрета используйте [готовую загрузку](../../odm-assets/SKILL.md#готовая-картинка).
  Не генерируйте другой арт, не создавайте pack/job и не вставляйте base64 в разговор.
- Успешный полный ответ записи уже является проверкой сохранения. После составного
  пакета достаточно **одного итогового чтения** `campaigns.get + members.list +
  sheets.list`: подтвердите настройки, кресло DM, ровно выбранных владельцев/PC,
  связи с библиотекой, изображение и показатели. Считайте PC по листам, а не по
  `playerCount`, куда может входить технический DM. Не выводите весь приватный payload.
- Сообщите ссылку `/campaigns/<id>`, состав, режим/сложность/строгость и фактический
  статус. По запросу «создай» оставьте лобби; запуск и ведение требуют задания на игру.
- При таймауте/потере транспорта сохраните полученные ID и точную неоднозначную
  операцию. Перед повтором найдите кампанию по owner/title, героя по owner/name,
  копию по `libraryCharacterId/userId` или картинку через `get_image`.
  Возобновляйте только отсутствующие шаги; create/instantiate/upload вслепую не повторяйте.
  Для narrator-записей остаются обязательными commandId/expectedSeq/timelineEpoch/readAfter.

## Контрольные сценарии без live-записей

1. «Создай пустой стол, владелец известен»: capabilities + список + один create;
   нет users, сюжета, персонажей или запуска без задания.
2. «Создай стол с несколькими существующими героями и этой картинкой»:
   один list на владельца, настройки в create, join → DM-seat → instantiate,
   прямой set_image и одно итоговое чтение; библиотечные герои не пересозданы.
3. «После рестарта продолжи, последний instantiate завершился таймаутом»:
   сначала чтение состава/листов, найденная копия не дублируется;
   выполняются оставшиеся шаги, приватный outline не публикуется.
